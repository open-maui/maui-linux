# ARM64 (linux-arm64)

OpenMaui apps can be published for `linux-arm64` (Raspberry Pi 4/5 and other aarch64 boards, Snapdragon and Ampere machines, arm64 VMs). The templates list both `linux-x64` and `linux-arm64` in `RuntimeIdentifiers`, and the package carries an aarch64 build of every native library it ships.

```bash
dotnet publish -c Release -r linux-arm64 --self-contained -o ./publish
```

Status: built, packaged and inspected on every release (below); not yet run on arm64 hardware by the maintainers. Reports from arm64 users are welcome.

## Native assets

| Asset | Source | linux-arm64 |
|-------|--------|-------------|
| `libopenmaui_wl.so` (Wayland protocol shim) | this repo, `native/` | Yes, since 10.0.110.1 (`runtimes/linux-arm64/native/`) |
| `libSkiaSharp.so` | SkiaSharp.NativeAssets.Linux 4.152.1 | Yes |
| `libHarfBuzzSharp.so` | HarfBuzzSharp.NativeAssets.Linux 14.2.1.201 | Yes |
| Harmony (runtime patching of MAUI Essentials) | Lib.Harmony 2.4.2 | Yes: MonoMod.Core carries an Arm64 detour backend and `exhelper_linux_arm64.so` |
| Tmds.DBus, Svg.Skia, CommunityToolkit.Maui.MediaElement, MAUI | NuGet | Managed only |
| libwayland, libxkbcommon, libX11, GTK 3, EGL/GLES, GStreamer, WPE WebKit, WebKitGTK, CUPS, AT-SPI2 | distribution packages | Yes on every supported distribution; WPE WebKit 2.54 for Fedora 43/44 aarch64 is in the `philn/wpewebkit` COPR |

Nothing x64-only remains in the packages. The only remaining gap is test coverage: no arm64 hardware run.

## The Wayland protocol shim

`libopenmaui_wl.so` holds the `wl_interface` tables for the protocols libwayland-client does not ship (xdg-shell, xdg-decoration, fractional-scale, viewporter, text-input-v3, primary-selection). It is generated by `wayland-scanner` and contains only data: 17 exported `*_interface` objects, three references to libwayland-client's core interfaces (`wl_surface`, `wl_seat`, `wl_output`), no code and no libc calls.

Before 10.0.110.1 it was built and packaged for x64 only, and the package's build targets copied the x64 file next to the app for every build, so a `linux-arm64` publish contained an x86-64 shim, `dlopen` failed, and native Wayland could not start (X11/XWayland still worked).

### Building it

`native/build.sh` builds both architectures:

```bash
native/build.sh                         # regenerate sources, build x64 and arm64
native/build.sh --no-regen --arch arm64 # rebuild only the arm64 library from the committed sources
```

| Output | Toolchain |
|--------|-----------|
| `native/libopenmaui_wl.so` (x86-64) | gcc, `-lwayland-client` |
| `native/linux-arm64/libopenmaui_wl.so` (aarch64) | clang `--target=aarch64-linux-gnu` + an LLVM linker (`ld.lld`, `$LLD`, or the `rust-lld` from a rustup toolchain) |

The arm64 build needs no aarch64 sysroot and installs nothing. Sources are compiled freestanding against the host's `wayland-util.h` (the structures are pointers and ints, laid out identically on LP64 x86-64 and aarch64), with empty shims for the libc headers the generated code includes. A throwaway stub `libwayland-client.so.0` defining the three core interfaces is linked in so the result records `DT_NEEDED libwayland-client.so.0`, like the x64 build, and binds to the real libwayland at load time. If clang or a linker is missing, the x64 library is still built and the script says the arm64 one was skipped.

Both libraries are committed; CI packs them as they are and does not run the script.

### Verification (10.0.110.1)

```
$ file native/linux-arm64/libopenmaui_wl.so
ELF 64-bit LSB shared object, ARM aarch64, version 1 (SYSV), dynamically linked, not stripped

$ readelf -d native/linux-arm64/libopenmaui_wl.so
 (NEEDED)   Shared library: [libwayland-client.so.0]
 (SONAME)   Library soname: [libopenmaui_wl.so]
 (FLAGS)    BIND_NOW
 (FLAGS_1)  Flags: NOW
 ...
```

- Exported symbols: the same 17 `*_interface` objects as the x64 library, with identical sizes (`nm -D -S` on x64 against `readelf --dyn-syms` on arm64: no differences).
- Undefined symbols: `wl_surface_interface`, `wl_seat_interface`, `wl_output_interface`, as on x64.
- Relocations: `R_AARCH64_RELATIVE` and `R_AARCH64_ABS64` only (pointer fix-ups in the data tables).
- Segments aligned to 64 KiB, so the library also loads on 64 KiB-page arm64 kernels.

### How the shim is found at run time

`WaylandWindow.TryLoadProtocols` `dlopen`s, in order: `libopenmaui_wl.so` next to `OpenMaui.Controls.Linux.dll`, then `runtimes/linux-x64/native/` and `runtimes/linux-arm64/native/` under that directory, then the bare name (so `LD_LIBRARY_PATH` works). A library of the wrong architecture fails to `dlopen` and the next candidate is tried. `OPENMAUI_DOCTOR=1` reports which file was loaded.

How the right file gets there:

| Scenario | What ends up in the output |
|----------|----------------------------|
| PackageReference, `dotnet publish -r linux-arm64` (or `-r linux-x64`), self-contained or not | NuGet copies the RID's `runtimes/<rid>/native/libopenmaui_wl.so` to the output root. The package's targets add nothing. |
| PackageReference, no RuntimeIdentifier (`dotnet build`, `dotnet run`) | NuGet puts both RIDs under `runtimes/<rid>/native/`; the package's targets also copy the build machine's architecture next to the app. |
| ProjectReference to `OpenMaui.Controls.Linux.csproj` (samples, tests) | The x64 shim is copied next to the assembly and the arm64 one to `runtimes/linux-arm64/native/`; on an arm64 machine the x64 copy fails to load and the arm64 one is used. |

Checked by publishing the `openmaui-linux-app` template against the locally packed 10.0.110.1 package:

| Command | `libopenmaui_wl.so` | `libSkiaSharp.so` / `libHarfBuzzSharp.so` |
|---------|---------------------|-------------------------------------------|
| `publish -r linux-arm64 --self-contained false` | aarch64 | aarch64 |
| `publish -r linux-arm64 --self-contained true` | aarch64 (every `.so` in the output, runtime included, is aarch64) | aarch64 |
| `publish -r linux-x64 --self-contained false` | x86-64 (loads; `openmaui doctor` reports it on KDE Wayland) | x86-64 |
| `build` (no RID) | x86-64 next to the app, x86-64 and aarch64 under `runtimes/` | all RIDs under `runtimes/` |

## Known limits

- Not run on arm64 hardware yet. The interop structures the platform declares are LP64 and match on both architectures (for example the GStreamer `GstMessage` type offset and the Vulkan structs), and Linux aarch64 passes variadic arguments like fixed ones, so no difference is expected, but it is unverified.
- 32-bit ARM (`linux-arm`) and musl RIDs are not supported: no shim is built for them.
- WPE plus DRM/KMS for embedded and kiosk targets without a desktop environment is future work (see `docs/ROADMAP.md`).
